# Tooling

- When a bug lives in an installed dependency, fix it via the pnpm patch workflow (`pnpm patch` → edit → `pnpm patch-commit`) so the change is captured in `patches/` and survives reinstall — instead of editing node_modules directly or forking. Confidence: 0.8
- In `@actual-app/api@26.9.0`, `@actual-app/core` is bundled into `dist/index.js`, so fixes to Actual's internals (e.g. the `advanceSchedulesService` null-db race) must be patched in the api package's bundle, not in the standalone `@actual-app/core` package files. Confidence: 0.8
- Verify changes in this project by running `pnpm test` and `pnpm typecheck` at the end. Confidence: 0.8
- When a dependency patch is the proposed fix, the user prefers to hear alternative approaches first (e.g. repo-side guards, architectural changes, waiting on upstream) with trade-offs laid out before committing to the patch. Confidence: 0.6
- Given a choice between a dependency patch, a filtered/uncaught-exception workaround, and a repo-side architectural fix, the user prefers the architectural fix that eliminates the root cause (e.g. choosing to hold a resource open for the process lifetime over masking the failure with a global `unhandledRejection` filter). Patches are acceptable as secondary guards, not as the primary fix — but once the root-cause fix makes a patch unnecessary, the user expects the patch to be reverted too ("revert the patches"), keeping dependencies on untouched upstream builds rather than retaining defensive patches. Confidence: 0.8
- When an application log line is deliberately sanitized (e.g. this project's `PROCESSING_FAILED` diagnostics expose only a `diagnosticId`, stage, and errorCode with no cause), don't ask the user to re-run it for details first — reproduce locally: start the service with the real `.env`/`data/`, exercise the failing endpoint the same way the UI would, and inspect persisted state directly (read-only `better-sqlite3` node one-liners against `data/actual-budget-importer.sqlite`) to rule causes in or out. Confidence: 0.6
- Use caution with write operations during repro: local reproduction may hold the port from a running container and point at the user's live budget — publishing/importing into the user's real Actual budget without prior confirmation is not acceptable; prefer read-only inspection and confirm any state-mutating publish/import/delete against live data first. Confidence: 0.7
- When an architectural change introduces a long-lived resource, add an explicit lifecycle/teardown method (`close()`) wired into process shutdown (SIGINT/SIGTERM) rather than leaving cleanup implicit. Confidence: 0.6
- Check CI status with the `gh` CLI: `gh run list --limit N` for recent runs, `gh run view <id> --log-failed` (optionally piped through `grep` for error lines / context) to diagnose failures, and `gh run watch <id> --exit-status` to wait on an in-flight run. Confidence: 0.7
- Project CI caveat: the Dockerfile's early layer copies only `package.json`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml` (not `patches/`), so adding `patchedDependencies` breaks `pnpm install --frozen-lockfile` in the container build; the push-triggered CI path for this repo is the "Publish container" workflow (the "Validate" workflow hasn't run on recent main pushes). If patches are ever reintroduced, the Dockerfile needs a `COPY patches/` step first. Confidence: 0.7
